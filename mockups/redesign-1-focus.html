Architect

Decide only the things that are expensive to change later: who can see whose data, where secrets live, what it talks to.

To pass: Every decision is written down with its reason — and you know what happens if each one turns out wrong.
Why this stage matters
Get these wrong and you pay forever; get them right and everything else is fast and loose.
⚠ 3 traps novices hit here
Copying architecture from a tutorial. The CRM needed a separate database per customer — it stores children's data. This app uses one shared DB with user_id tags. Isolation is a per-app decision, not a religion.

Secrets ending up in code 'temporarily'. API keys pasted into source get scraped by bots within minutes of pushing to GitHub. Env vars from line one, always.

Step 1 · Talk it through

MentorTwo strangers both use DogWalkr — should either ever see the other's clients?
YouNo way — that would be a disaster. One walker seeing another's client list.
MentorExactly — so every record needs an owner tag. Write that down as your first decision. Now: what does your app need passwords or keys for?

Step 2 · Write it down

QUESTION 2 OF 4
What does your app need passwords or keys for?
Just list them — your builder stores these as 'environment variables', never in the code.
💡 A real answer looks like: 'AI key for the mentor, email key for sending, database password.'
